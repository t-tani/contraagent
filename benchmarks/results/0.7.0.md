# Scheduling in 0.7.0: no idle slot, and the finish chance

The queue of this release keeps one invariant: no slot idles while a task can
start. Near a deadline, a late task (one whose finish chance is below
`FINISH_CHANCE`, 0.35) goes after every other task and starts when a slot is
still free. The queue defers it only when other tasks take every slot. The
finish chance is the share of the samples of the task's tail key that fit in the
time left, where 0.6.2 compared one median.

`main.json` and `main.md` hold the figures of this queue. `0.7.0-before.json`
holds those of the tree it was built on, with value dependencies and the queue
of 0.6.2, measured on the same machine just before. All runs use 20 seeds, the
default scale and Python 3.12.9. From 0.7.0 on, the benchmark's
`docs_one_review` awaits each task call, as the demo does; `0.6.2.json` measured
the version that did not wait.

Without a deadline the queue is the same, and the changes are the noise of real
sleeps and threads: a few percent in the makespan, more in the idle time, which
is a small difference of two large numbers. Under a deadline the work done by it
moves by -2.2% to +5.9%; only the second run of `time-box` gains more than the
noise. Fewer tasks are deferred, so more of them run past the deadline: a longer
makespan there is work that ran, and the cost after the deadline over the six
deadline runs grows from 6.70 to 7.28 USD (`main.md`). The plan expected this
cost of starting a task that may not finish when no other work wants the slot.

Deferral now happens only when the slots are full. In these scenarios they
usually are near the deadline, so most deferrals of the earlier queue were of
that kind already, and the gain is small. The `would fit` column counts a
deferred task whose own duration was shorter than the time left; it leaves out
the work after the task, which the finish chance counts, so it overstates what a
deferral cost.

## Against 0.6.2

`compare benchmarks/results/0.6.2.json benchmarks/results/main.json`: in the
second run, every scenario without a deadline has a median makespan from 5.2%
shorter to 0.7% longer than 0.6.2's, within the plan's limit of 5% worse. Under
the deadline the work done by it grows in the second run by 7.7%
(`demo-deadline`), 3.5% (`demo-one-review-deadline`) and 10.1% (`time-box`).

## Seeding a first run: not added

The rule compares the first run of the async `docs` with the first run of
0.6.2's `docs_one_review`, which created its tasks without waiting. Seeding
applies when the first run is 10% or more worse, and the second run brings the
gap within 5%.

| figure | first run | second run | rule |
|---|---|---|---|
| makespan | -2.2% (shorter) | +5.8% | does not hold |
| done by deadline | +2.2% worse | -5.0% (more work) | does not hold |

The first run is not worse than 0.6.2's flow that created its tasks early, so
there is nothing for a seed to recover. The previous run's structure stays a
prediction for the monitor's forecast; the queue does not read it.

## The threshold: 0.35

The deadline scenarios with `FINISH_CHANCE` at 0.5, 0.35 and 0.2, measured one
after another on the same tree (medians; work in minutes, cost in USD):

| scenario | run | work at 0.5 | at 0.35 | at 0.2 | cost at 0.5 | at 0.35 | at 0.2 |
|---|---|---|---|---|---|---|---|
| demo-deadline | first | 36.20 | 36.73 | 35.70 | 0.82 | 0.86 | 1.16 |
| demo-deadline | second | 37.66 | 38.23 | 38.56 | 0.88 | 0.83 | 0.86 |
| demo-one-review-deadline | first | 34.64 | 35.22 | 33.71 | 0.87 | 0.80 | 1.01 |
| demo-one-review-deadline | second | 34.94 | 37.43 | 35.38 | 1.66 | 1.60 | 1.54 |
| time-box | first | 63.10 | 63.10 | 62.62 | 1.46 | 1.49 | 1.64 |
| time-box | second | 60.27 | 63.55 | 61.44 | 1.62 | 1.46 | 1.63 |
| total | | 266.81 | 274.26 | 267.41 | 7.31 | 7.04 | 7.84 |

The rule takes the threshold with the most work done by the deadline whose cost
after the deadline is not more than at 0.5. At 0.35 the work is as large or
larger in every run (2.8% in total) and the cost is 3.7% lower in total, so 0.35
is the threshold. An earlier measurement of `demo-deadline` and `time-box` alone
found the same order of work, with the cost of 0.35 4% above that of 0.5; the
cost differs by about the noise between two measurements, and the work does not.
The journal of real runs may show another distribution, which the plan names as
the next input to this choice. `main.json` is the run at 0.35, so its figures
differ from this table's column by that noise.

## An arrival share: not added

Every fourth start given to the earliest arrival that can start, against the
same queue at threshold 0.5: the largest makespan grows by 24.5% in the first
run of `competing` and shrinks by at most 4.7% elsewhere, and the median makespan
of `demo` grows by 7.9% in the first run. The plan asks for a largest makespan
10% shorter and a median no more than 2% worse, so the share is not added.

The variants were run by setting the queue's internal constant, or by wrapping
its order, before `benchmarks/schedule.py` ran; neither is an option of the
tool, because the tool uses only the public API.
