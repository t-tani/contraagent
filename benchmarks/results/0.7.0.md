# Scheduling in 0.7.0: no idle slot, and the finish chance

The queue of this release keeps one invariant: no slot idles while a task can
start. Near a deadline, a late task (one whose finish chance is below
`FINISH_CHANCE`) goes after every other task and starts when a slot is still
free. The queue defers it only when other tasks take every slot. The finish
chance is the share of the samples of the task's tail key that fit in the time
left, where 0.6.2 compared one median.

`main.json` and `main.md` hold the figures of this queue. `0.7.0-before.json`
holds those of the tree it was built on, with value dependencies and the queue
of 0.6.2, measured on the same machine just before. All runs use 20 seeds, the
default scale and Python 3.12.9. The `demo-one-review` scenarios do not run
from 0.7.0 on, because the release refuses a `Pending` among the params of a
task call. For the same reason the benchmark's `docs` now awaits `prepare`
before it calls `summarize`; `prepare` is a Python task that takes no time here,
so the figures of 0.6.2 still compare.

Without a deadline the queue is the same, and the changes are the noise of real
sleeps and threads (a few percent). Under a deadline the work done by it moves
by less than 3% either way. Fewer tasks are deferred, so the runs last longer
after the deadline: a longer makespan there is work that ran, and its cost after
the deadline is in `main.md` (0.40 → 0.65 USD for `demo-deadline` in the second
run, 1.49 → 1.65 USD for `time-box`).

Deferral now happens only when the slots are full, and in these scenarios they
usually are near the deadline: most deferrals of the earlier queue were of that
kind already. The `would fit` column counts a deferred task whose own duration
was shorter than the time left; it leaves out the work after the task, which the
finish chance counts, so it overstates what a deferral cost.

## Against 0.6.2

`compare benchmarks/results/0.6.2.json benchmarks/results/main.json`: in the
second run, every scenario without a deadline has a median makespan 0.1% to 6.7%
shorter than 0.6.2's, within the plan's limit of 5% worse. Under the deadline
the work done by it grows by 7.5% (`demo-deadline`) and 2.1% (`time-box`) in the
second run.

## Seeding a first run: not added

The rule compares the first run of the async `docs` with the first run of
0.6.2's `docs_one_review`. Seeding applies when the first run is 10% or more
worse, and the second run brings the gap within 5%.

| figure | first run | second run | rule |
|---|---|---|---|
| makespan | -2.7% (shorter) | +4.1% | does not hold |
| done by deadline | +1.2% worse | -4.8% (more work) | does not hold |

The first run is not worse than 0.6.2's flow that created its tasks early, so
there is nothing for a seed to recover. The previous run's structure stays a
prediction for the monitor's forecast; the queue does not read it.

## The threshold: 0.5 kept

`demo-deadline` and `time-box` with `FINISH_CHANCE` set to 0.35 and 0.2 (medians;
work and cost in minutes and USD):

| threshold | scenario | run | done by deadline | cost after deadline |
|---|---|---|---|---|
| 0.5 | demo-deadline | first | 36.19 | 0.75 |
| 0.5 | demo-deadline | second | 37.73 | 0.65 |
| 0.5 | time-box | first | 63.10 | 1.40 |
| 0.5 | time-box | second | 60.27 | 1.65 |
| 0.35 | demo-deadline | first | 36.20 | 0.89 |
| 0.35 | demo-deadline | second | 38.23 | 0.70 |
| 0.35 | time-box | first | 63.10 | 1.49 |
| 0.35 | time-box | second | 63.88 | 1.55 |
| 0.2 | demo-deadline | first | 36.47 | 1.04 |
| 0.2 | demo-deadline | second | 38.45 | 0.72 |
| 0.2 | time-box | first | 63.10 | 1.61 |
| 0.2 | time-box | second | 61.81 | 1.98 |

The rule takes the threshold with the most work done by the deadline whose cost
after the deadline is not more than at 0.5. A lower threshold does a little more
work (at most 1.9% in `demo-deadline`, and 6% in one run of `time-box`), and it
costs more after the deadline in three runs of four. So 0.5 stays. The journal
of real runs may show a different distribution, which the plan names as the next
input to this choice.

## An arrival share: not added

Every fourth start given to the earliest arrival that can start, against
`main.json`: the largest makespan grows by 24.5% in the first run of `competing`
and shrinks by at most 4.7% elsewhere, and the median makespan of `demo` grows
by 7.9% in the first run. The plan asks for a largest makespan 10% shorter and a
median no more than 2% worse, so the share is not added.

The variants were run by setting the queue's internal constant, or by wrapping
its order, before `benchmarks/schedule.py` ran; neither is an option of the
tool, because the tool uses only the public API.
